## Architecture decisions

### Headless CMS + separate frontend

Payload 3 handles content authoring and serves a REST API. Astro consumes this API server-side. This keeps the admin UI and public site decoupled, so the CMS can be deployed independently and the frontend can be replaced without changing content.

### Astro render strategy (SSR, static, or hybrid)

**Status: Decided.**

- Render strategy: `output: 'static'`. Pages prerender to static HTML at build time; server routes (`/preview`, `/api/contact`) opt out individually via `export const prerender = false`. Astro v5+ folded the old `hybrid` mode into `static`, so there's no separate "hybrid" output value to choose between.
- Both CMS and frontend deploy on **Railway**, in the same project.
- Because content is baked into static HTML at build time, publishing in the CMS does not update the live site until `web` rebuilds. This is automated: `cms/src/hooks/triggerWebDeploy.ts` commits a fresh timestamp to `web/.build-trigger` via the GitHub API on publish (`afterChange`/`afterDelete` on `Pages`, `Projects`, `Posts`, `Navigations`; `afterChange` on the `SiteSettings`, `ProjectsPage`, and `Navigation` globals), which Railway's GitHub integration then builds on push.
- A direct Railway deploy-API trigger (without a real file change) doesn't reliably bust the build cache — Railway's build cache is content-addressed, so redeploying an unchanged commit reuses the previous build's output byte-for-byte, including stale CMS content. A genuine commit is the only thing that reliably forces a fresh build.
- Accepted trade-off: every publish adds a small commit to `git log`. Low priority to change — see `CLAUDE.md` → "Rebuild on publish" for the fuller writeup and a possible future alternative (building `web` outside Railway via CI, deploying the finished artifact directly).

### Image delivery — migration to Cloudflare Image Transformations

**Status: In progress (from 2026-09-10).** Frontend code has landed on `image_optimisations`, gated behind the `PUBLIC_IMAGE_CDN_BASE` env var — unset, the site behaves exactly as before (Sharp `imageSizes`). Remaining: the Cloudflare dashboard / DNS work (below), then set the env var in Railway and verify, then a cleanup commit.

Today, responsive images are pre-generated by Payload/Sharp on upload (five fixed `webp` sizes at quality 82) and served from Cloudflare R2 via the `pub-…​.r2.dev` public URL. `web/src/components/MediaItem.astro` builds the `srcset` from the stored `sizes` map. See "Images and responsive delivery" in `web/CLAUDE.md` for the current pipeline.

**Proposal:** replace the fixed Sharp size ladder with on-the-fly **Cloudflare Image Transformations** (the `/cdn-cgi/image/…` URL form).

Benefits:

- `format=auto` negotiates AVIF → WebP → original per the request `Accept` header — AVIF (20–50% smaller than WebP on photographic content) delivered safely, with **no `<picture>` element and no double storage**. Serving multiple formats still counts as **one** transformation.
- Arbitrary widths on demand — delete the five-entry `imageSizes` ladder; store one bounded original (~2560–3000px) as the transform source.
- Cropping becomes a URL param (`fit=cover` + `width`/`height` + `gravity`). Payload already stores `focalX`/`focalY` on every Media doc and the focal-point editor is already in the admin UI (was a no-op) — `gravity=${focalX/100}x${focalY/100}` now drives every crop (default 50/50 = centre). The focal-point editor is the crop-focus control; `gravity=auto` is **not** used, so crops are deterministic and editor-controlled.
- Same change adds `loading="lazy"` (below-the-fold) / `loading="eager" fetchpriority="high"` (LCP — hero background only, via a `priority` prop) to `MediaItem.astro`, which it lacked entirely.

**This supersedes the earlier "Phase 1" quick-win idea** (lower Sharp `webp` quality to ~72, add a ~2000px tier, cap the original). Those tweaks all either become a Cloudflare URL param (`quality=72`) or fold into this work, so there's no point shipping them separately to a pre-launch site.

#### Cost

- Cloudflare **Free** plan: **5,000 unique transformations / month**, then **$0.50 per 1,000**. No egress fees.
- A "unique transformation" = one `(source image + exact parameter set)` combo, counted **once per calendar month** — cache serves repeats; static Astro builds emit identical URLs for every visitor; stable R2 filenames mean the CMS-publish rebuild does not churn the count.
- Estimate for this site: ~30–40 distinct source images × ~5 `srcset` widths ≈ **150–300 unique transformations/month** to render the whole site — roughly 10× headroom under the free tier.
- **No surprise-bill risk on the Free plan:** exceeding quota returns error `9422` (image fails to load), *not* a charge. Cost requires an explicit upgrade to a paid Images plan.
- Budget multipliers to avoid: deriving `width` from the exact viewport (snap to a fixed ~5-value ladder instead); long width ladders; multiple distinct crop aspect ratios of the same image.

#### DNS implications — this is the blocker

Cloudflare URL transformations only run on a domain that is a **full Cloudflare zone** (nameservers pointed at Cloudflare). The client's domain is currently on GoDaddy (registration **and** DNS, serving a GoDaddy-hosted holding page).

- This is a **nameserver change, not a domain transfer** — registration stays at GoDaddy, no transfer fee, no 60-day lock. Add the site to Cloudflare, let it import the existing records, switch nameservers at GoDaddy.
- **Free plan is sufficient** for URL transformations — no Pro/Business requirement. (Partial / CNAME-only setup that keeps DNS at GoDaddy is Business-plan only — not worth it here.)
- The R2 bucket must be reachable from that zone: **bind it to a custom domain** on the client's Cloudflare zone (e.g. `media.<clientdomain>`) instead of the current `pub-…​.r2.dev` URL — already recommended in `CLAUDE.md` → "Cloudflare R2 setup". Alternatively, allow the `r2.dev` URL under Transformations → source origins.
- Risks during the nameserver move: **email** (MX + SPF/DKIM/DMARC TXT records must be recreated *exactly* first, or mail breaks), the **holding page** (A/CNAME records must carry over), and any other subdomains / domain-verification TXT records. Safe order: add to Cloudflare → verify the imported record set matches GoDaddy's zone exactly → *then* switch nameservers. Propagation is usually < 1 hour.
- **Shared dependency:** the client's Cloudflare account with us granted access is *already* a pending prerequisite for Cloudflare Turnstile on the contact form (see "Assumptions / unknowns"). Same account, same access — do them together.

**Dev-time workaround (unblocks implementation before the client's DNS moves):** run transformations on any domain already on Cloudflare (or a cheap throwaway added to Cloudflare Free), with the R2 bucket bound to a subdomain of it. The web app reads the transformation base URL from an env var, so swapping to `media.<clientdomain>` at launch is a one-line config change.

### Pages collection instead of Globals

All pages (Home, FAQs and future pages) are documents in a single `Pages` collection. Each document has a `slug` field that maps to its URL. Astro uses `pages/index.astro` for the home slug and `pages/[slug].astro` as a catch-all for other pages.

This allows CMS editors to create a new page (for example, Services) without developer changes to route files.

**Nested pages / `parent`.** A page can select a `parent` (another page). The `slug` field stores the **full path** — the `slug` field's `beforeValidate` hook prepends the parent's stored slug (e.g. parent `services` + segment `web-design` → `services/web-design`), and `pages/[...slug].astro` renders it from that. Because that hook only ever prepends the *immediate* parent's slug and never re-runs on children, a `cascadeSlugToChildren` `afterChange` hook (`cms/src/hooks/cascadeSlugToChildren.ts`) re-derives every descendant's slug whenever a published page's slug changes (parent added, moved, or renamed). It re-saves each direct child so its own `beforeValidate` recomputes against the updated parent, recursing down the subtree; a per-request visited set guards against `parent` cycles. `afterChangeTriggerDeploy` dedupes on `req.context` so the subtree re-save still triggers only one web rebuild.

Most pages are block-based. Current exceptions under discussion:

- News collection pages
- Projects collection pages

These may use predefined templates/fields, with optional block content appended after templated content.

Contact was originally one of these exceptions (a hard-coded templated page) but is no longer — it's now a regular block-based `Pages` document, using a dedicated `ContactForm` block (`cms/src/blocks/ContactForm.ts`) with expanded options to replicate the previous templated layout.

### Shared block system (Payload Blocks field)

Page content is built from shared block types. Blocks are defined once in `cms/src/blocks/` and imported into any collection or global that needs flexible content. This is equivalent to ACF Flexible Content in WordPress: adding a new block type in one place makes it available wherever that block set is used.

Each block has an **Anchor ID** field for hash-link navigation.

## Common block options

- **Padding**: Editor chooses top, bottom, or both; size options are small, medium, large, or extra-large. These map to custom Tailwind spacing classes.
- **Anchor ID**: String used for hash anchor links. No spaces; alphanumeric plus `-` and `_` only.

## Block definitions

### Hero

- **Heading Part 1**: One text style
- **Heading Part 2**: Another text style
- **Intro**: Textarea field.
- **Buttons**: Array field. Each button includes:
  - Label/text
  - Type: scroll to section (anchor), open video (self-hosted), or page link
  - Variant: solid or outline
  - Colour: white or green
  - Conditional fields based on selected button type
- **Background media**: Image, video, or GLSL shader (single option currently).
- **Overlay alpha**: Adjustable opacity to improve text contrast.

### Text and Media

Two variants:

1. **Split viewport variant**: media spans 50% viewport width and 100vh on wide viewports.
2. **Contained grid variant**: text and media are constrained in a 12-column container, each taking half width on wide viewports.

Fields:

- Heading text field (supports double-curly-brace emphasis)
- Body copy (WYSIWYG)
- Media position (left or right)
- Media type (image or self-hosted video, muted/loop/autoplay)

For the contained variant, selectable media aspect ratios:

- 4:3, 16:9, square, 3:4, or auto

### Media

- Image or video
- Video behavior: background playback (muted, looped, autoplay)
- Optional button opens unmuted video in a dialog
- Optional heading with selectable heading style
- Overlay alpha option when text is present
- Size options: full screen, large (container width), small
- Aspect ratio options available
